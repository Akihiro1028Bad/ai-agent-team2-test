# 設計書: Issue #3 - ユーザープロフィール画面を追加したい

## 1. 概要

ユーザーのプロフィール情報（ユーザー名・メールアドレス・アバター画像・自己紹介文）を閲覧できる画面を追加する。表示のみの読み取り専用画面とし、`GET /api/users/:id` エンドポイントからデータを取得する。モバイル対応のシンプルなカードレイアウトで実装する。

---

## 2. 背景・動機

現状、アプリケーションにユーザーのプロフィールを確認できる画面が存在しない。ユーザー同士の相互理解や、自身のアカウント情報の確認のために、プロフィール閲覧機能が求められている。

---

## 3. 影響範囲

### 変更するファイル

| ファイル | 変更内容 |
|---------|---------|
| `src/pages/UserProfilePage.tsx` | 新規作成。プロフィール画面のページコンポーネント |
| `src/components/UserProfileCard.tsx` | 新規作成。プロフィール情報を表示するカードコンポーネント |
| `src/hooks/useUser.ts` | 新規作成。`GET /api/users/:id` を呼び出すカスタムフック |
| `src/types/user.ts` | 新規作成。`User` 型定義 |
| `src/router.tsx`（または相当するルーティング定義ファイル） | `/users/:id` ルートを追加 |

### 影響を受ける既存機能

- **ルーティング**: 既存のルーター設定に新規ルートを追加するため、ルーティング定義ファイルに変更が入る
- **認証・セッション**: 今回のスコープでは認証連携は行わないが、将来的に「自分のプロフィール」と「他ユーザーのプロフィール」を分ける際は認証フローへの影響が生じる

---

## 4. 実装方針

### アプローチ

1. **型定義** (`src/types/user.ts`)
   APIレスポンスに対応する `User` インターフェースを定義する。

2. **データ取得フック** (`src/hooks/useUser.ts`)
   `GET /api/users/:id` を `fetch` または既存の HTTP クライアントで呼び出し、`loading` / `error` / `user` の3ステートを返すカスタムフックを実装する。

3. **カードコンポーネント** (`src/components/UserProfileCard.tsx`)
   `User` を props として受け取り、アバター・ユーザー名・メールアドレス・自己紹介文をカードレイアウトで表示する。レスポンシブ対応（モバイルファースト）。

4. **ページコンポーネント** (`src/pages/UserProfilePage.tsx`)
   URLパラメータから `:id` を取得し、`useUser` フックでデータを取得。ローディング中はスケルトン or スピナーを、エラー時はエラーメッセージを表示する。

5. **ルーティング登録**
   `/users/:id` に `UserProfilePage` を紐付ける。

### 代替案

| 案 | 内容 | 不採用理由 |
|----|------|-----------|
| 編集機能の同時実装 | 閲覧・編集を1画面にまとめる | 今回のスコープ外。複雑性を上げるため別Issueで対応 |
| `/profile` の固定URL | ログイン中ユーザー自身のみ表示 | 将来的な他ユーザー閲覧を考慮し `:id` パラメータ方式を採用 |
| SSR / サーバーコンポーネント | Next.js App Router のサーバーサイド取得 | プロジェクト構成が未確定のためクライアントサイドフェッチで統一 |

---

## 5. データ構造の変更

### 新規型定義: `User`

```typescript
// src/types/user.ts

export interface User {
  id: string;
  name: string;          // 表示名 / ユーザー名
  email: string;         // メールアドレス
  avatarUrl: string;     // アバター画像 URL
  bio: string;           // 自己紹介文
}
```

DBスキーマへの変更は今回のスコープに含まない（バックエンドAPIは既存の `GET /api/users/:id` を利用する）。

---

## 6. API変更

### 利用するエンドポイント（既存）

| メソッド | パス | 説明 |
|---------|------|------|
| `GET` | `/api/users/:id` | 指定IDのユーザー情報を取得 |

#### レスポンス例

```json
{
  "id": "u_123",
  "name": "Akihiro",
  "email": "akihiro@example.com",
  "avatarUrl": "https://example.com/avatars/u_123.png",
  "bio": "TypeScript好きのエンジニアです。"
}
```

#### エラーレスポンス

| ステータス | 対応 |
|-----------|------|
| `404 Not Found` | 「ユーザーが見つかりません」メッセージを表示 |
| `500 Internal Server Error` | 汎用エラーメッセージを表示し、リトライを促す |

**新規エンドポイントの追加・変更はなし。**

## 7. テスト方針

### ユニットテスト

| 対象 | テスト内容 |
|------|-----------|
| `useUser` フック | 正常取得・ローディング状態・エラー状態それぞれのステート遷移 |
| `UserProfileCard` コンポーネント | 各フィールドが正しくレンダリングされるか。`avatarUrl` が空の場合のフォールバック表示 |

### 統合テスト（E2E）

| シナリオ | 期待結果 |
|---------|---------|
| `/users/u_123` にアクセス | プロフィールカードが表示される |
| 存在しないIDにアクセス | 404エラーメッセージが表示される |
| APIがタイムアウト / 5xx を返す | エラー状態のUIが表示される |

### レスポンシブ確認

- モバイル（375px〜）
- タブレット（768px〜）
- デスクトップ（1280px〜）

## 8. リスク・懸念事項

| リスク | 影響度 | 対応策 |
|-------|--------|--------|
| `GET /api/users/:id` のレスポンス仕様が未確定 | 高 | バックエンド担当者と事前にスキーマを合意する。型定義はAPIレスポンスに合わせて随時修正 |
| アバター画像の読み込み失敗 | 低 | `<img>` の `onError` ハンドラでデフォルト画像にフォールバック |
| 認証なしで任意IDのプロフィールが閲覧できる | 中 | 今回スコープ外だが、将来的に認証・認可の追加を検討。Issueを起票しておく |
| メールアドレスの公開 | 中 | プライバシーポリシーおよびバックエンド側のアクセス制御を確認する |
